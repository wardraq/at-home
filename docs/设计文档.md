# AtHome — 产品设计文档

> 产品名：**AtHome** — 「回家的照片，自动存档」
> 
> 一个极简的 iOS App，连上家里的 WiFi 后自动把照片增量同步到本地硬盘（Mac / PC）。

**它不是什么：**
- 不是照片浏览器（Apple 相册已经做得很好）
- 不是云备份工具（iCloud 已经做了）
- 不是照片编辑工具

**核心场景只有一条：**
用户在家、手机连上家庭 WiFi、充电或空闲时，自动把新照片备份到本地存储。

---

## 二、"在家"检测方案

### 方案对比

| 方案 | 实现难度 | App Store 上架 | 推荐度 |
|------|---------|----------------|--------|
| 读取 WiFi SSID 匹配 | 低（个人版），高（上架需要特殊权限） | 很难过审 | ⭐⭐⭐ 个人自用推荐 |
| 连接本地服务器验证 | 低 | 可以过审 | ⭐⭐⭐⭐ 推荐 |
| 用户手动触发 | 最低 | 可以过审 | ⭐⭐ 体验差 |
| GPS 地理位置 | 中 | 可以过审 | ⭐ 耗电，过度 |

### 推荐方案：本地服务器可达性检测（无需 SSID 权限）

原理：用户在家里的 Mac / NAS 上运行一个极轻量的接收程序，iOS App 尝试访问这个程序的地址（`http://192.168.x.x:port/ping`），能通就说明在家。

优点：
- 不需要任何特殊 iOS 权限
- 可以正常上 App Store
- 即使用户带手机到朋友家，连的是外部网络，也检测不到本地服务器，不会误触发
- 用户可以自定义"家"的地址

### 备选方案：WiFi SSID 检测（仅自用 / TestFlight）

如果是个人自用、不打算上 App Store，可以直接读取当前 WiFi 的 SSID，匹配用户预设的 WiFi 名称列表。

- iOS 13+ 需要 `Access WiFi Information` 能力
- 个人签名 / TestFlight 可以用
- App Store 审核对这类权限审查很严，单纯"备份照片"可能无法过审

## 三、配对与握手验证

### 为什么需要握手

同一局域网内可能有多个设备，接收端需要确认"来上传照片的手机是我认可的"，手机端也需要确认"我连的接收端是我的，不是别人伪装的"。双向验证，防止误连和恶意上传。

### 接收端唯一标识（UUID）

每个接收端在首次启动时生成并永久保存一个 UUID，作为该接收端的唯一标识。

- UUID 在接收端首次启动时自动生成（如 `A3F2-8B1C-E591-4D7A`），存在本地配置文件
- 用户在手机端配对时，需要同时提供：**接收端 UUID + 验证码**
- 相比只用验证码，加入 UUID 后：
  - 验证码通常只有 6 位，暴力尝试有可能猜中；UUID + code 的组合空间巨大，无法暴力破解
  - 如果用户有多台接收端（家里 Mac + 公司 Mac），各有不同 UUID，手机端不会搞混
  - 换路由器、换网络环境后，只要 UUID 和 code 没变，照样能配对

### 配对流程

```
首次配对：
1. 本地接收端首次启动 → 自动生成 UUID，保存在本地配置
2. 用户在本地接收端设置验证码（6位数字，或更长的 token）
3. 本地端显示配对信息：UUID + 验证码（建议生成二维码，手机扫码一次性带入）
4. 用户在 iOS App 设置里输入相同的 UUID + 验证码（或扫码）
5. 手机端发起握手请求，携带 UUID + 验证码
6. 本地端同时验证 UUID 和验证码，都匹配则握手成功
7. 握手成功后，后续所有上传请求都携带 sessionToken
```

### 握手协议设计

```
1. 手机端 → 本地端: POST /handshake
   Body: {
     "uuid": "A3F2-8B1C-E591-4D7A",
     "code": "123456",
     "deviceName": "iPhone 15 Pro"
   }

2. 本地端验证：
   a. uuid 是否匹配本地 UUID
   b. code 是否匹配本地验证码
   - 都匹配 → 返回 { "status": "ok", "sessionToken": "abc..." }
   - uuid 不匹配 → 返回 { "status": "error", "message": "接收端 UUID 不匹配" }
   - code 不匹配 → 返回 { "status": "error", "message": "验证码错误" }
   - 本地未设置验证码 → 返回 { "status": "error", "message": "请先在接收端设置验证码" }

3. 后续上传请求 Header 携带:
   Authorization: Bearer <sessionToken>

4. 每次上传时本地端验证 sessionToken，不通过则拒绝
```

### 验证码与 UUID 规则

- 接收端 UUID：**首次启动时自动生成**，用户不需要手动设置，只需在配对时读取并输入到手机端
- 验证码：**用户主动设置**，默认不设置时拒绝所有上传（安全默认）
- 手机端配对信息（UUID + code）存在 Keychain，配对成功后长期有效
- 支持修改验证码：修改后需要重新握手，旧 sessionToken 失效
- 支持扫码配对：本地端显示包含 UUID + code 的二维码，手机端扫码自动填入

### 安全边界

- UUID + 验证码**只用于局域网内的配对验证**，不替代 HTTPS
- 如果需要更高安全性，接收端可以生成自签名证书，手机端 pin 住证书（后续优化）
- 第一版用 UUID + 验证码 + HTTP 即可，简单有效

## 四、同步协议与接收端方案

### 方案 A：iOS App → HTTP 接收端（推荐）

```
[iOS App] --HTTP POST--> [本地接收端: Mac / NAS / 树莓派]
```

**接收端选项：**

1. **Mac 菜单栏 Companion App**（体验最好）
   - 轻量 SwiftUI 菜单栏 App
   - 内建 HTTP Server（接收照片）
   - 可配置存储路径（外接硬盘、指定文件夹）
   - 显示接收进度和日志

2. **Python / Node 脚本**（最轻量，给懂技术的用户）
   - 一个 `receive.py` 脚本，运行 `pip install flask && python receive.py`
   - 接收 HTTP POST，按日期目录存储照片
   - 用户自己确保脚本在运行

3. **支持 SMB / WebDAV**（通用 NAS 用户）
   - iOS App 直接通过 SMB 或 WebDAV 协议写入 NAS
   - 不需要额外的接收端程序
   - 需要在 iOS App 里配置 NAS 地址、用户名、密码

**推荐组合：**
- 第一版做 **HTTP 接收端 + Mac Companion App**，体验最完整
- 后续可加 SMB 直写 NAS 的支持

## 五、增量同步逻辑

### 核心思路

用 PhotoKit 的 `localIdentifier` 作为照片的唯一 ID，在 iOS App 本地维护一个"已同步集合"。

```
同步流程：
1. 检测是否在家（本地接收端是否可达）
2. 握手验证（验证码是否匹配）
3. 检查是否允许同步（可配置：仅充电时、仅 Wi-Fi、手动确认等）
4. 通过 PhotoKit 获取所有照片的 localIdentifier + modificationDate
5. 与本地已同步集合比对，找出新增 / 修改的照片
6. 按时间顺序（从旧到新）上传这些照片
7. 上传成功后，将 localIdentifier 写入已同步集合
8. 全部完成后，通知用户（本地通知）
```

### 去重与冲突处理

- **新增照片：** `localIdentifier` 不在已同步集合中 → 上传
- **编辑过的照片：** `localIdentifier` 在集合中但 `modificationDate` 更新 → 重新上传，覆盖
- **已存在跳过：** `localIdentifier` 在集合中且 `modificationDate` 未变 → 跳过
- **本地已删的照片：** 不同步删除操作（本地备份保留，防止误删）

### 存储结构（接收端）

```
Photos Backup/
├── 2024/
│   ├── 01/
│   │   ├── IMG_001.HEIC
│   │   └── IMG_002.JPG
│   └── 02/
├── 2025/
│   └── 03/
└── Videos/
    └── 2025/
```

按拍摄日期（EXIF / PhotoKit 的 `creationDate`）分目录，原始文件名或 `YYYYMMDD_HHMMSS` 格式。

## 六、iOS App 功能清单

### 必须有的功能

- [ ] **配对配置**
  - 配置接收端地址（`http://192.168.x.x:8080`）
  - 配置接收端 UUID（手动输入或扫码）
  - 配置验证码（与本地端一致才能握手）
  - 测试连接（Ping + 握手验证按钮）
  - 可配置"信任的 WiFi 名称"（可选，作为额外判断）

- [ ] **同步触发**
  - 打开 App 时自动检测并触发同步
  - 可配置：仅充电时同步
  - 可配置：仅每天同步一次（避免频繁触发）
  - 后台：利用 iOS 后台刷新 + 本地通知提醒（有限，不保证）

- [ ] **增量同步**
  - 通过 PhotoKit 读取照片
  - 维护已同步 ID 列表
  - 只上传新增 / 修改的照片

- [ ] **同步状态**
  - 上次同步时间
  - 本次同步进度（X / Y 张）
  - 同步成功 / 失败通知
  - 失败重试（手动或下次自动）

- [ ] **存储管理**
  - 显示已同步照片数量
  - 清除同步记录（重新全量同步）

### 不需要的功能

- ❌ 照片浏览（Apple 相册更好）
- ❌ 照片编辑
- ❌ 云端存储
- ❌ 分享功能
- ❌ 人脸识别 / 相册整理

## 七、Mac Companion App 功能清单

极轻量菜单栏 App，主要是一个正在运行的接收服务。

- [ ] **接收服务开关**
  - 启动 / 停止 HTTP 接收服务
  - 显示服务地址（如 `http://192.168.1.100:8080`）

- [ ] **配对信息展示**
  - 显示本机 UUID（首次启动时自动生成，永久保存）
  - 显示 / 重新生成二维码（包含 UUID + 验证码，供手机端扫码配对）
  - 显示当前已配对的设备列表

- [ ] **验证码配置**
  - 设置 / 修改验证码
  - 未设置验证码时拒绝所有上传
  - 修改验证码后，已配对设备的 sessionToken 失效，需重新握手

- [ ] **存储路径配置（MVP：单路径）**
  - 选择备份目录（单块硬盘）
  - 显示已接收照片数量、占用空间
  - 📌 未来迭代：支持配置多个备份路径，照片同时写入多块硬盘（本地镜像冗余）

- [ ] **接收日志**
  - 显示最近接收的照片
  - 错误日志

- [ ] **开机自启动（可选）**

## 八、技术栈建议

### iOS App

- **语言：** Swift + SwiftUI
- **照片访问：** PhotoKit（`PHAsset`, `PHImageManager`）
- **网络：** `URLSession` 后台上传
- **本地存储：** `UserDefaults`（同步记录）+ Core Data / SQLite（大量照片时）
- **后台：** Background Tasks（`BGAppRefreshTask`）+ 本地通知

### Mac Companion App

- **语言：** Swift + SwiftUI（菜单栏 App）
- **HTTP Server：** `Vapor`（完整）或 `GCDWebServer`（轻量）或 `SwiftNIO`
- 最轻量方案：`URLSession` 做 HTTP 服务器其实不够，推荐 `GCDWebServer`（ObjC/Swift，很轻）

### 接收端脚本（备选）

- **Python：** `flask` + `werkzeug`
- **Node：** `express`

## 九、分阶段实施计划

### Phase 1：MVP（最小可用）

- iOS App：手动触发同步，HTTP POST 上传照片
- 接收端：Python 脚本（`receive.py`）
- 验证码握手：两端设置相同验证码，握手通过才能上传
- 验证核心流程：握手验证 → PhotoKit 读取 → 增量判断 → HTTP 上传 → 本地存储

### Phase 2：自动触发

- iOS App：打开 App 自动检测 + 触发同步
- 家的检测：接收端可达性检测
- 同步状态界面

### Phase 3：Mac Companion App

- 替换 Python 脚本，做菜单栏 App
- 更好的接收体验

### Phase 4： polish

- 后台同步优化
- 错误重试
- 充电时仅同步选项
- 多设备支持（iPad）

### Phase 5（未来迭代）：多路径冗余备份

- 支持配置多个备份路径（多块硬盘）
- 照片同时写入所有在线路径
- 某块硬盘离线时警告，但继续写其他在线硬盘
- 显示每块硬盘状态（在线/离线、剩余空间）

## 十一、未来迭代方向

以下功能不在 MVP 范围内，作为后续版本规划：

### 1. 多路径本地镜像

- 支持配置多个备份路径，照片同时写入多块硬盘
- 一块硬盘损坏时，照片仍可从其他硬盘恢复
- 硬盘离线检测和警告

### 2. 异地云备份

- 本地备份完成后，可选加密上传到云存储（iCloud / 阿里云 OSS / Backblaze B2）
- 端到端加密，云端无法读取照片内容
- 遵循 3-2-1 备份原则，真正保证照片安全

### 3. 备份完整性校验

- 接收端存照片时同时存 CRC / 哈希值
- 定期校验，发现损坏文件时提醒用户

### 4. NAS 直连支持

- 除 HTTP 接收端外，直接支持 SMB / WebDAV 协议写入 NAS
- 不需要运行额外的接收端程序

### 5. Android 端

- 目前只做 iOS，后续可扩展 Android 端
- 接收端复用同一套协议，无需修改

## 十、关键决策记录

1. **没有照片浏览功能** — Apple 相册已经完美，不需要重复造轮子
2. **单向同步（手机 → 本地）** — 不需要反向同步，本地备份是归档性质
3. **增量同步** — 用 `localIdentifier` + `modificationDate` 判断，不重复上传
4. **本地接收端地址可配置** — 用户可以用 Mac、NAS、树莓派，灵活
5. **不过度设计后台同步** — iOS 后台限制多，以"打开 App 触发"为主，后台为辅
6. **UUID + 验证码握手配对** — 接收端首次启动自动生成 UUID，手机端配对时需同时提供 UUID + 验证码；未设置验证码时默认拒绝所有上传；支持扫码配对
7. **MVP 先做单路径备份，多路径镜像作为未来迭代** — 第一版只支持单块硬盘，降低复杂度，验证核心流程后再扩展
8. **产品名定为 AtHome** — 「回家的照片，自动存档」，简洁有力，直接点题
