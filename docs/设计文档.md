# AtHome — 产品设计文档

> 产品名：**AtHome** — 「回家的照片，自动存档」
> 
> 一个极简的 iOS App，连上家里的 WiFi 后自动把照片增量同步到本地硬盘（Mac / PC）。
>
> 服务端 API、数据模型与存储规则的详细定义见 **[服务端 API 文档](./api-server.md)**，本文档与之保持一致。

**它不是什么：**
- 不是照片浏览器（Apple 相册已经做得很好）
- 不是云备份工具（iCloud 已经做了）
- 不是照片编辑工具

**核心场景只有一条：**
用户在家、手机连上家庭 WiFi、充电或空闲时，自动把新照片备份到本地存储。

## 二、"在家"检测方案

### 方案对比

| 方案 | 实现难度 | App Store 上架 | 推荐度 |
|------|---------|----------------|--------|
| 读取 WiFi SSID 匹配 | 低（个人版），高（上架需要特殊权限） | 很难过审 | ⭐⭐⭐ 个人自用推荐 |
| 连接本地服务器验证 | 低 | 可以过审 | ⭐⭐⭐⭐ 推荐 |
| 用户手动触发 | 最低 | 可以过审 | ⭐⭐ 体验差 |
| GPS 地理位置 | 中 | 可以过审 | ⭐ 耗电，过度 |

### 推荐方案：本地服务器可达性检测（无需 SSID 权限）

原理：用户在家里的 Mac / NAS 上运行一个极轻量的接收程序，iOS App 尝试访问这个程序的地址（`http://192.168.x.x:port/ping`），能通就说明在家。

优点：
- 不需要任何特殊 iOS 权限
- 可以正常上 App Store
- 即使用户带手机到朋友家，连的是外部网络，也检测不到本地服务器，不会误触发
- 用户可以自定义"家"的地址

### 备选方案：WiFi SSID 检测（仅自用 / TestFlight）

如果是个人自用、不打算上 App Store，可以直接读取当前 WiFi 的 SSID，匹配用户预设的 WiFi 名称列表。

- iOS 13+ 需要 `Access WiFi Information` 能力
- 个人签名 / TestFlight 可以用
- App Store 审核对这类权限审查很严，单纯"备份照片"可能无法过审

## 三、配对与握手验证

### 为什么需要握手

同一局域网内可能有多个设备，**手机端（资产方）必须确认"我要上传的这台服务器确实是我的"**，防止局域网里有人伪装成你的接收端来偷照片。服务端也需要确认"这个 userId 是我授权的"，决定照片存到哪个用户目录。

**核心安全方向：客户端验证服务端（防伪装服务器偷照片） > 服务端验证客户端（防未授权上传）。**

### 多用户模型

服务端维护一个用户列表，每个"用户"对应一台授权的手机：

```json
// 服务端基础配置：config.json（不含 sessionToken 和上传记录）
{
  "serverId": "srv-F2A8B1C3D4E5",
  "storagePath": "/Volumes/Backup/Photos",
  "apiPort": 6060,
  "adminPort": 6061,
  "users": [
    {
      "id": "usr-a3f28b1ce5914d7a",
      "name": "wardraq",
      "status": "active",
      "createdAt": "2025-07-01T15:00:00+08:00"
    },
    {
      "id": "usr-b7c1d4e5f6a7890b",
      "name": "妈妈",
      "status": "active",
      "createdAt": "2025-07-01T15:30:00+08:00"
    }
  ]
}
```

sessionToken 与上传元数据与 config 隔离，分别存于 **sessions**（内存 + 落盘）和 **metadata.db**（SQLite），详见 [api-server.md §八](./api-server.md#八持久化数据模型)。

### 设计要点：userId 合一，无需验证码

- **userId 同时充当身份标识和认证凭证** — userId 是 UUID 级别的长随机串（128-bit），不可暴力猜，比 6 位验证码安全得多
- **去掉验证码** — QR 码本身就是安全通道（物理在场才能扫描），userId 已足够认证
- **用户名不可改** — 创建后锁定，直接作为存储目录名，避免 rename 风险
- **每个手机独立凭证** — 可单独吊销某一台手机，不影响其他设备

### 配对流程

```
首次配对：
1. 服务端首次启动 → 自动生成 serverId，保存在本地配置
2. 管理员在 Admin Web UI（:6061）创建新用户（输入 name） → 服务端生成 userId
3. 服务端生成二维码，包含：serverId + userId + serverAddress
4. 手机扫码 → 存到 Keychain（serverId, userId, serverAddr）
5. 手机端发起握手请求，携带 userId + deviceName
6. 服务端验证 userId 是否在用户列表中且 active → 通过后返回 serverId + sessionToken + userName
7. 手机端验证返回的 serverId 是否与扫码存储的 serverId 一致 → 一致则信任 sessionToken
8. 握手成功后，后续上传请求携带 Bearer sessionToken
```

### 握手协议设计

```
1. 手机端 → 服务端: POST /handshake
   Body: {
     "userId": "usr-a3f28b1ce5914d7a",
     "deviceName": "iPhone 15 Pro"
   }
   // 注意：不发送 serverId，手机不需要告诉服务器"你是谁"
   // serverId 由服务器在响应中亮明，供手机验证

2. 服务端验证：
   a. userId 是否在用户列表中
   b. 用户 status 是否 active
   - 都通过 → 返回 { "status": "ok", "serverId": "srv-F2A8B1C3D4E5", "sessionToken": "st-abc...", "userName": "wardraq", "expiresAt": "..." }
   - userId 不存在 → 返回 { "status": "error", "message": "用户未授权" }
   - userId 已 revoked → 返回 { "status": "error", "message": "用户已被吊销" }

3. 手机端验证（关键安全步骤）：
   a. 响应中的 serverId 是否与 Keychain 中存储的 serverId 一致？
   - 一致 → 信任 sessionToken，后续上传使用
   - 不一致 → 可能是伪装服务器，断开连接，不传照片

4. 后续上传请求 Header 携带:
   Authorization: Bearer <sessionToken>

5. 每次上传时服务端验证 sessionToken，不通过则拒绝
```

### 二码（QR 码）内容设计

```
二维码 payload:
{
  "serverId": "srv-F2A8B1C3D4E5",    // 服务端身份标识（手机用来"对暗号"）
  "userId":  "usr-a3f28b1ce5914d7a", // 用户凭证（身份 + 认证合一）
  "addr":    "192.168.1.100:6060"    // 手机端 API 地址（不含协议前缀）
}

手机扫码后一次性拿到所有信息，零手动输入。
```

### sessionToken 管理规则

- sessionToken 由服务端在握手成功后签发，存储在独立的 **sessions** 存储中（内存热查 + 落盘持久化），与 config.json 隔离
- sessionToken 设 TTL（7 天），超期必须重新握手（重新验暗号）
- 连接中断后不复用旧 token，需重新握手
- 用户被吊销 → 该用户所有 sessionToken 立即失效
- 同一用户可同时持有多个有效 sessionToken（支持多设备用同一 userId 配对）

### 安全边界与评估

- **握手验一次 serverId 即信任后续 sessionToken** — 在 HTTP 明文环境下，每次验 serverId 也无法防 MITM（攻击者可伪造响应中的 serverId），验证一次已达到 HTTP 层面的安全上限
- **防配置错误/误连** — serverId 对暗号可有效防止用户连错邻居服务器
- **防扫描错误 QR** — 手机存储的 serverId 与服务器返回的不一致时立即断开
- **不防主动中间人攻击** — ARP 欺骗 + HTTP 明文下，MITM 可同时窃听和伪造；真正防护需 HTTPS + 证书 pin（Phase 2）
- userId + HTTP 即是 MVP 的务实安全方案，简单有效

## 四、同步协议与接收端方案

### 方案 A：iOS App → HTTP 接收端（推荐）

```
[iOS App] --HTTP POST--> [本地接收端: Mac / NAS / 树莓派]
```

### 双端口架构

| 端口 | 绑定地址 | 用途 | 访问方 |
|------|----------|------|--------|
| **6060** | `0.0.0.0` | 手机端 API（ping / handshake / upload） | 局域网内 iOS App |
| **6061** | `127.0.0.1` | 管理端 Web UI + Admin API | 仅本机浏览器 |

Admin 通过独立端口仅监听 localhost，不暴露给局域网。MVP 阶段 Python 脚本和 Mac Companion App 均提供极简 Web UI 用于用户管理与配对。

### 服务端 API

完整请求/响应契约见 [api-server.md](./api-server.md)。

**手机端 API（:6060）**

| 端点 | 说明 | 认证 |
|------|------|------|
| `GET /ping` | 手机检测可达性 | 无 |
| `POST /handshake` | userId + deviceName → serverId + sessionToken + userName | userId 验证 |
| `POST /upload` | Bearer sessionToken + 照片文件 + 元数据（单张） | sessionToken |

**管理端 API（:6061，仅 localhost）**

| 端点 | 说明 |
|------|------|
| `GET /` | Admin Web UI 首页 |
| `GET /admin/status` | 服务状态、存储路径、磁盘空间 |
| `GET /admin/users` | 查看用户列表 |
| `POST /admin/users` | 创建用户（name → 生成 userId + QR） |
| `DELETE /admin/users/{userId}` | 吊销用户（所有 token 失效） |
| `GET /admin/users/{userId}/qrcode` | 获取配对 QR 码 |
| `GET /admin/uploads/recent` | 最近上传记录 |
| `PUT /admin/settings` | 更新存储路径等配置 |

未来可扩展 `POST /upload/batch` 批量上传接口。

**接收端选项：**

1. **Mac 菜单栏 Companion App**（体验最好）
   - 轻量 SwiftUI 菜单栏 App
   - 内建 HTTP Server（接收照片）
   - 可配置存储路径（外接硬盘、指定文件夹）
   - 显示接收进度和日志

2. **Python / Node 脚本**（最轻量，给懂技术的用户）
   - 一个 `receive.py` 脚本，运行 `pip install flask && python receive.py`
   - 双端口：6060 接收上传，6061 提供 Admin Web UI
   - 接收 HTTP POST，按用户 + 日期目录存储照片，元数据写入 SQLite
   - 用户自己确保脚本在运行

3. **支持 SMB / WebDAV**（通用 NAS 用户）
   - iOS App 直接通过 SMB 或 WebDAV 协议写入 NAS
   - 不需要额外的接收端程序
   - 需要在 iOS App 里配置 NAS 地址、用户名、密码

**推荐组合：**
- 第一版做 **HTTP 接收端 + Mac Companion App**，体验最完整
- 后续可加 SMB 直写 NAS 的支持

## 五、增量同步逻辑

### 核心思路

用 PhotoKit 的 `localIdentifier` 作为照片的唯一 ID，在 iOS App 本地维护一个"已同步集合"。

```
同步流程：
1. 检测是否在家（本地接收端是否可达）
2. 握手验证（userId 认证 + serverId 对暗号确认服务端身份）
3. 检查是否允许同步（可配置：仅充电时、仅 Wi-Fi、手动确认等）
4. 通过 PhotoKit 获取当前所有照片 → phoneIDs（Set）
5. 从本地存储获取已同步记录 → syncedIDs（Set）
6. 集合运算：
   - phoneIDs ∩ syncedIDs → 已同步且手机还在的照片（跳过）
   - phoneIDs - syncedIDs → 新照片或未同步（需要上传）
   - syncedIDs - phoneIDs → 手机已删但本地备份还在（已归档，不处理）
7. 对需要上传的照片，再判断 modificationDate：
   - ID 不在 syncedIDs → 新照片，上传
   - ID 在 syncedIDs 但 modificationDate 变了 → 编辑过，重新上传（服务端分配新版本号）
8. 按时间顺序（从旧到新）上传；Live Photo 分两次上传（part=image + part=video）
9. 上传成功后，将 localIdentifier + modificationDate 写入已同步集合
10. 全部完成后，通知用户（本地通知）

**职责分工：** iOS 判断「要不要传」（localIdentifier + modificationDate）；服务端分配 version、落盘、写 metadata（详见 [api-server.md §五](./api-server.md#五版本与幂等规则)）。手机端**不上传** version 字段。
```

### 各场景处理策略

| 场景 | iOS 行为 | AtHome 处理 | 说明 |
|------|---------|------------|------|
| **新增照片** | 新 localIdentifier | 上传到本地 | 正常流程 |
| **编辑照片** | localIdentifier 不变，modificationDate 变 | 重新上传，服务端分配新 version，**旧版本文件保留** | 服务端维护版本号，依据 modificationDate 递增 |
| **删除照片** | localIdentifier 从 PhotoKit 消失（30天后永久删） | **本地备份保留**，不删本地文件 | 本地是归档，手机删不代表要删备份 |
| **复制照片** | 产生新 localIdentifier，内容相同 | 当新照片处理，照常上传 | MVP 不按哈希去重；后续迭代加去重 |
| **Live Photo** | 一个 ID = 图片 + 视频 | 分两次上传（part=image + part=video） | 文件名基于消毒后的 localIdentifier + version |
| **连拍 Burst** | 多个独立 localIdentifier | 每张独立同步 | 每张是独立的 PHAsset |

### 删除照片的进度影响（关键逻辑）

手机删除照片后，PhotoKit 的照片总数会减少，但已同步记录里仍有被删照片的 ID。如果直接用 `总数 - synced.count` 计算待同步数，会出现负数。

**正确的进度算法：**

```
phoneIDs = PhotoKit 当前所有照片的 localIdentifier（Set）
syncedIDs = 本地存储所有已同步的 localIdentifier（Set）

手机当前照片数 = phoneIDs.count
待同步 = (phoneIDs - syncedIDs).count           ← 新/未同步的照片
已同步 = (phoneIDs ∩ syncedIDs).count           ← 手机还在 + 已备份的
已归档 = (syncedIDs - phoneIDs).count           ← 手机删了但本地保留的
```

这样永远不会出现负数，且「已归档」有独立信息价值。

### 同步进度界面设计

```
┌─────────────────────────────────────┐
│  AtHome 同步状态                      │
│                                     │
│  手机照片    5,230 张                  │
│  已同步      5,200 张  ████████████99%│
│  待同步      30 张                     │
│  已归档      50 张（手机已删，本地保留） │
│                                     │
│  上次同步    今天 10:00                │
│  当前状态    同步中 12/30              │
└─────────────────────────────────────┘
```

### 同步数据存储设计

#### iOS 端（SQLite / Core Data）

```
SyncedPhoto 表:
| localIdentifier | modificationDate | syncedAt |
|---|---|---|
| id-1 | 2025-06-15T08:30 | 2025-07-01T10:00 |
| id-2 | 2025-06-16T09:00 | 2025-07-01T10:00 |
```

- 只存 ID + 时间戳，不删已归档记录（手机删了照片，记录仍保留）
- 查进度时做集合运算（phoneIDs vs syncedIDs），逻辑清晰无负数
- 显示信息（文件名、大小等）从 PhotoKit 实时查询，不存本地
- MVP 先用 UserDefaults 存 `[String: Date]` 映射，3000+ 照片后迁移到 SQLite

#### 本地接收端

**不维护**手机端「已同步集合」（增量逻辑在 iOS），但需在 SQLite（metadata.db）记录上传元数据与版本信息，用于：

- 版本分配（依据 modificationDate）
- Admin 展示（最近上传、统计）
- 上传幂等（同 modificationDate 重传不产生新版本）

核心职责：
- 收照片 → 按规则落盘
- 验证 token → 拒绝非法请求
- 分配 version → 编辑时保留历史版本文件

### 存储结构（接收端，按用户隔离）

文件名基于消毒后的 `localIdentifier`（`/` → `_`）+ version + part，而非原始文件名。`localIdentifier` 是 PhotoKit 系统 ID（如 `A1B2C3D4-.../L0/001`），详见 [api-server.md §6](./api-server.md#六存储规则)。

```
Photos Backup/
├── wardraq/                  ← 用户 name（不可改），顶层按用户隔离
│   ├── 2024/
│   │   ├── 01/
│   │   │   ├── A1B2C3D4-..._L0_001_v1_image.HEIC
│   │   │   ├── A1B2C3D4-..._L0_001_v1_video.mov   ← Live Photo 视频部分
│   │   │   └── B2C3D4E5-..._L0_001_v1_image.JPG
│   │   └── 02/
│   └── 2025/
│       └── 07/
│           ├── ..._v1_image.HEIC
│           ├── ..._v2_image.HEIC                  ← 编辑后新版本，v1 仍保留
│           └── ..._v2_video.mov
├── 妈妈/                     ← 另一台配对的手机
│   ├── 2025/
│   └── ...
```

按拍摄日期（请求中的 `creationDate`）分 YYYY/MM 子目录，顶层按用户 name 隔离。

## 六、iOS App 功能清单

### 必须有的功能

- [ ] **配对配置**
  - 扫描服务端二维码 → 自动获取 serverId + userId + serverAddr（零手动输入）
  - 测试连接（Ping + 握手验证按钮）
  - 可配置"信任的 WiFi 名称"（可选，作为额外判断）

- [ ] **同步触发**
  - 打开 App 时自动检测并触发同步
  - 可配置：仅充电时同步
  - 可配置：仅每天同步一次（避免频繁触发）
  - 后台：利用 iOS 后台刷新 + 本地通知提醒（有限，不保证）

- [ ] **增量同步**
  - 通过 PhotoKit 读取照片
  - 维护已同步 ID 列表（SQLite：localIdentifier + modificationDate）
  - 集合运算：phoneIDs vs syncedIDs，计算待同步/已同步/已归档
  - 只上传新增 / 修改的照片

- [ ] **同步状态**
  - 手机当前照片数（PhotoKit 实时查询）
  - 已同步数（手机还在 + 已备份）
  - 待同步数（新/未同步）
  - 已归档数（手机已删但本地保留）
  - 上次同步时间
  - 当前同步进度（X / Y 张）
  - 同步成功 / 失败通知
  - 失败重试（手动或下次自动）

- [ ] **存储管理**
  - 显示已同步照片数量
  - 清除同步记录（重新全量同步）

### 不需要的功能

- ❌ 照片浏览（Apple 相册更好）
- ❌ 照片编辑
- ❌ 云端存储
- ❌ 分享功能
- ❌ 人脸识别 / 相册整理

## 八、技术栈建议

### iOS App

- **语言：** Swift + SwiftUI
- **照片访问：** PhotoKit（`PHAsset`, `PHImageManager`）
- **网络：** `URLSession` 后台上传
- **本地存储：** MVP 用 UserDefaults 存 `[localIdentifier: Date]` 映射，3000+ 照片后迁移 Core Data / SQLite
- **后台：** Background Tasks（`BGAppRefreshTask`）+ 本地通知

### Mac Companion App

- **语言：** Swift + SwiftUI（菜单栏 App）
- **HTTP Server：** `Vapor`（完整）或 `GCDWebServer`（轻量）或 `SwiftNIO`
- 最轻量方案：`URLSession` 做 HTTP 服务器其实不够，推荐 `GCDWebServer`（ObjC/Swift，很轻）
- **双端口：** 6060（手机 API）+ 6061（Admin Web UI，127.0.0.1）

### 接收端脚本（备选）

- **Python：** `flask` + `werkzeug` + `qrcode`
- **Node：** `express`
- **数据库：** SQLite（metadata.db）

### Phase 1：MVP（最小可用）

## 十一、未来迭代方向

以下功能不在 MVP 范围内，作为后续版本规划：

### 1. 多路径本地镜像

- 支持配置多个备份路径，照片同时写入多块硬盘
- 一块硬盘损坏时，照片仍可从其他硬盘恢复
- 硬盘离线检测和警告

### 2. 异地云备份

- 本地备份完成后，可选加密上传到云存储（iCloud / 阿里云 OSS / Backblaze B2）
- 端到端加密，云端无法读取照片内容
- 遵循 3-2-1 备份原则，真正保证照片安全

### 3. 备份完整性校验

- 接收端存照片时同时存 CRC / 哈希值
- 定期校验，发现损坏文件时提醒用户

### 4. NAS 直连支持

- 除 HTTP 接收端外，直接支持 SMB / WebDAV 协议写入 NAS
- 不需要运行额外的接收端程序

### 5. Android 端

- 目前只做 iOS，后续可扩展 Android 端
- 接收端复用同一套协议，无需修改

## 十、关键决策记录

1. **没有照片浏览功能** — Apple 相册已经完美，不需要重复造轮子
2. **单向同步（手机 → 本地）** — 不需要反向同步，本地备份是归档性质
3. **增量同步** — 用 `localIdentifier` + `modificationDate` 判断，不重复上传
4. **本地接收端地址可配置** — 用户可以用 Mac、NAS、树莓派，灵活
5. **不过度设计后台同步** — iOS 后台限制多，以"打开 App 触发"为主，后台为辅
6. **多用户模型 + userId 合一** — 服务端维护用户列表，每个用户有独立 userId（长随机串，身份+认证合一）和不可改的 name；去掉验证码，QR 码包含 serverId + userId + serverAddr；手机扫码零手动输入
7. **客户端验证服务端** — 安全方向是手机确认"服务器是我认过的"；握手时手机验证服务端返回的 serverId 是否匹配 QR 扫到的值，不匹配则断开不传照片；服务端同时验证 userId 是否授权
8. **双端口架构** — 手机 API 监听 `0.0.0.0:6060`；Admin Web UI 监听 `127.0.0.1:6061`，不暴露给局域网
9. **MVP 先做单路径备份，多路径镜像作为未来迭代** — 第一版只支持单块硬盘，降低复杂度，验证核心流程后再扩展
10. **产品名定为 AtHome** — 「回家的照片，自动存档」，简洁有力，直接点题
11. **删除照片不删本地备份** — 手机删照片后本地保留，归档性质；syncedIDs 不删除已归档记录，进度用集合运算避免负数
12. **编辑照片保留历史版本** — modificationDate 变了就重新上传；服务端分配新 version，旧版本文件保留在磁盘
13. **version 由服务端维护** — iOS 只传 modificationDate，不上传 version；服务端依据 modificationDate 变化递增版本号
14. **复制照片当新照片处理（MVP）** — 新 localIdentifier 直接上传；后续迭代按内容哈希去重
15. **同步数据用极简映射** — MVP 用 `[localIdentifier: modificationDate]` 存 UserDefaults，3000+ 后迁移 SQLite；显示信息从 PhotoKit 实时查；iOS 端无需存 version
16. **按用户隔离存储** — 目录顶层按用户 name（不可改）隔离：`Photos Backup/{userName}/YYYY/MM/`；文件名基于消毒后的 localIdentifier + version + part
17. **用户名创建后不可改** — 锁定后直接作为存储目录名，避免 rename 风险；如需改名只能重新创建用户
18. **sessionToken 独立存储** — sessions 与 config.json 隔离（内存 + 落盘），config 仅存基础配置和用户列表
19. **sessionToken TTL 7 天 + 断连重握手** — token 超期或连接中断后必须重新握手验暗号，不复用旧 token
20. **握手验一次 serverId 即信任后续 token** — HTTP 明文下每次验 serverId 也无法防 MITM（攻击者可伪造响应），验一次已达到 HTTP 层面安全上限；真正防中间人需 HTTPS + 证书 pin（Phase 2）
21. **服务端 metadata.db** — SQLite 记录上传元数据与版本信息（非手机端同步状态），用于 version 分配、Admin 展示和幂等
22. **Live Photo 分两次上传** — 同一 localIdentifier + modificationDate，part 分别为 image 和 video；静图统一 part=image
